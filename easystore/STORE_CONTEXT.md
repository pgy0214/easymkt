## 2026-08-24 — 최초 방향 설정

### 배경

사용자가 참고 사이트로 제시: https://shop.gprized.com/item/view/37
(네이버 플레이스 마케팅 서비스를 옵션선택+수량+가격으로 파는 쇼핑몰형 상세페이지 —
[구매]/[장바구니] 버튼, 옵션 드롭다운, 서비스설명/가격/리뷰/주의사항/문의 탭 구조)

지금 이지리뷰는 "실행형" 구조다:
- 광고주가 사업자등록증 승인을 받은 뒤 직접 매장·캠페인을 등록
- 캠페인 조건(수량/기간/리워드)을 광고주가 스스로 설계
- 관리자가 리뷰어를 배정하고, 리뷰어가 작업을 수행
- 정산은 후불

목표는 "상품형" 구조로 확장하는 것:
- 고객이 승인 절차 없이 가입 즉시 상품을 구매
- 정해진 상품(수량·가격 조합, 예: 영수증 리뷰 10/30/50건)을 고르고 결제
- 결제 즉시 캠페인이 자동 생성되어 실행 시작

### 핵심 판단 — 사이트를 완전히 분리한다

한 홈페이지 안에 구매 버튼을 끼워 넣는 방식이 아니라, **진입점부터 다른 두 개의 사이트**로 나눈다.

| | 실행 사이트 (지금 있는 것) | 상품판매 사이트 (새로 만들 것) |
|---|---|---|
| 대상 | 사업자등록 승인을 받은 광고주 | 승인 없이 가입 즉시 구매하는 일반 고객 |
| 진입 | 리뷰어 포털 · 광고주센터 · 관리자 (지금 그대로 유지) | 신규 진입점 (가칭 easymkt), 카탈로그·장바구니·결제 |
| 운영 방식 | 광고주가 캠페인 조건을 직접 설계 | 정해진 상품을 고르기만 하면 됨 |
| 정산 | 후불 | 선결제 (표준 쇼핑몰 방식) |

두 사이트가 공유하는 것은 **오직 뒤에서 돌아가는 실행 엔진(캠페인·Task·리뷰어 배정·정산)** 하나뿐이다.
상품판매 사이트에서 결제가 끝나면 그 주문이 실행 엔진에 캠페인 1건으로 꽂히고, 그 다음부터는
지금과 완전히 같은 방식(리뷰어 배정 등)으로 처리된다.

### 재사용 vs 신규 매핑

**그대로 재사용:**
- 리뷰어 배정·작업 실행 (Task/ReviewTarget 파이프라인) — 주문 1건 = 캠페인 1건으로 매핑만
- 체험단 캠페인 엔진 (ExperienceCampaign) — 상품 옵션에서 파라미터만 채워 넣도록 연결
- 매장/리뷰어 관리, 정산 — 관리자 쪽 운영 도구는 손댈 필요 없음
- 상품 소개 페이지 ("마케팅 이렇게 하세요", 2026-08-24에 이미 구현됨: `Product`/`Notice` 모델,
  `easyreview-backend/app/routers/products.py`, `notices.py`, 프론트 `ProductManager.jsx`,
  `NoticeManager.jsx`) — 카탈로그의 원형. 구매 버튼만 얹으면 됨

**새로 지어야 할 것:**
- 구매 가능한 상품(SKU) — 지금 `Product`는 "설명"만 있음. 수량·가격 옵션 조합 필요
- 장바구니·주문 — `Order`/`OrderItem`/`Customer`(사업자등록 없이 가입 가능한 가벼운 회원) 모델 신설
- 결제(PG) 연동 — 가장 큰 신규 작업. PG사(예: 토스페이먼츠) 가맹 심사에 시간이 걸리므로 **가장 먼저 착수**
- 결제 완료 → 자동 실행 연결 — 결제 웹훅 → OrderItem 내용으로 ReviewTarget/ExperienceCampaign 자동 생성
- 고객용 마이페이지 — 상품판매 사이트 안에 새로 만들되, 광고주센터 "내 캠페인" 뷰의 화면 패턴만 참고 (코드 공유 아님)

### 단계별 로드맵

1. **구매 가능한 상품(SKU) 만들기** — Product에 옵션 그룹(예: 리뷰 10/30/50건) + 옵션별 가격 추가,
   gprized처럼 "옵션선택" 드롭다운 + 가격 자동 표시
2. **장바구니·주문** — Order/OrderItem/Customer 모델
3. **결제 연동** — PG사 가맹 심사가 오래 걸리므로 1·2단계와 병행 착수 권장
4. **결제 완료 → 자동 실행 연결** — 이 전환의 핵심. 여기서부터는 기존 실행 엔진과 완전히 동일하게 동작
5. **고객 마이페이지·진행현황** — 주문내역 + 진행 상태만 있으면 충분

### 진행 전에 정해야 할 것 (사업 판단, 아직 미결정)

- **상품판매 사이트를 어디에 짓는가**: 같은 저장소 안에 별도 프론트엔드 앱(지금도 포털/광고주센터/
  관리자가 경로만 다른 구조라 API·인증 공유가 빠름) vs 완전히 별도 저장소/배포(브랜드 분리는 확실하지만
  API 연동을 별도 관리해야 해서 초기엔 더 무거움)
- **고정가 상품인가, 견적형(문의)인가**: gprized도 소액 상품은 즉시구매, 고액 패키지는 "단가 문의"로
  나눠서 운영. 이지리뷰도 초반엔 소액·표준화된 상품(리뷰 N건)부터 고정가로 시작하는 게 안전
- **선결제 구조로 정산 방식이 바뀌는 것을 감안했는가**: 지금은 캠페인 등록 후 후불 정산. 쇼핑몰은
  선결제가 표준이라 매출 인식 시점, 환불 정책(작업 중 취소 시 부분환불 등)을 새로 설계해야 함

## 2026-08-24 — 대상 고객 확정: 일반 소비자(대행사 아님)

사용자가 명확히 확인: 이 스토어는 **일반 소비자**를 대상으로 만드는 홈페이지다 — 리뷰
대행사·사업자가 아니라 (예: 자영업자가 직접, 또는 마케팅 대행사를 안 끼고) 자기 가게 리뷰를
사고 싶은 일반 개인/소상공인이 고객. 이로써 위 "진행 전에 정해야 할 것"의 사업자등록증 승인
관련 판단이 확정됨 — **승인 절차 없이 가입 즉시 구매** 방향 그대로 간다(별도 미결정 사항
아니었음, 처음 방향 설정 그대로 확정).

**적용**: UI/카피 톤을 대행사·전문 마케터가 아니라 비전문 소비자 눈높이에 맞출 것(전문 용어
최소화, 구매 흐름은 gprized 참고 레퍼런스처럼 단순하게). 로그인/가입도 사업자 서류 업로드 같은
승인 절차 없이 가벼운 회원가입(전화번호 등)으로 설계.

## 2026-08-24 (같은 날, 후속) — 실행 연결 방식 정정, 리뷰 시스템 추가, 개발 기간

### 정정: 주문→캠페인 연결은 자동이 아니라 관리자 수동

위 최초 로드맵의 "4단계: 결제 완료 → 자동 실행 연결(웹훅으로 자동 생성)"은 **사용자가 명시적으로
정정**함. 실제로 원하는 흐름:

1. 실행 사이트는 지금처럼 작업을 전체적으로 계속 진행한다 (변경 없음)
2. 스토어(상품판매 사이트)에서 소비자가 구매하면, **관리자가 그 주문 정보를 보고 실행 사이트에
   캠페인을 수동으로 개설**한다 (자동 웹훅 생성이 아님)

즉 필요한 건 "결제 웹훅 → 자동 ReviewTarget 생성" 같은 자동화 로직이 **아니라**, 관리자가
"결제완료됐지만 아직 캠페인으로 전환 안 된 주문" 목록을 확인하고, 그 정보를 참고해서 지금 있는
캠페인 등록 폼으로 직접 만들 수 있는 **주문 관리 화면**이다. 훨씬 단순하고 리스크가 적음 — 4단계
개발 범위가 크게 줄어듦.

(참고: 나중에 주문량이 많아지면 "이 정보로 캠페인 초안 채우기" 같은 반자동 보조 기능을 얹는 것도
가능하지만, 1차 목표는 아님)

### 추가 기능: 상품별 리뷰·평점 + 관리자 노출수 보정

스토어에서 각 상품에 대해 **구매한 회원이 리뷰(평점+후기)를 남길 수 있어야** 함 — gprized의
"리뷰 777개, 평점 5.0" 탭과 동일한 개념. 목적은 신뢰도(사회적 증거) — 많이 구매/후기가 쌓인
상품일수록 다른 고객이 안심하고 구매하게 됨.

추가로, **관리자가 노출되는 리뷰 "숫자"를 조정할 수 있어야 함** — 실제 리뷰 개수와 별개로
카드/상세페이지에 표시되는 숫자를 관리자가 보정(가산)할 수 있게. 설계 방향:
- 진짜 리뷰(구매자 작성, 평점+텍스트, Order와 연결해 "구매확정" 표시 가능)는 그대로 쌓이고
- Product에 `표시 리뷰수 보정치`(정수, 기본 0) 필드를 추가해서, 화면에 보여줄 때 `실제 리뷰수 + 보정치`로 계산
- 리뷰 본문 자체를 조작하는 게 아니라 "숫자"만 보정하는 가벼운 방식으로 시작 (요청 원문이
  "그 숫자를 관리자가 조정"이라고 명시)

이 기능은 로드맵에 **6단계: 리뷰·평점 시스템**으로 추가. 2단계(주문/Customer)가 있어야 "구매확정
리뷰" 판별이 되므로 2단계 이후 아무 때나 착수 가능 — launch를 막는 필수 단계는 아님.

### 개발 기간 추정

정확한 일정은 실제 착수 전까지 확정하기 어렵지만, 오늘 세션에서 공지사항/상품소개 기능 전체
(백엔드 모델+라우터, 프론트 관리자 화면 2개, 광고주센터 노출, 배포)를 한 세션 안에 끝낸 속도를
기준으로 잡으면:

| 단계 | 추정 작업량 |
|---|---|
| 1. SKU/옵션/가격 | 반나절~1일 |
| 2. 장바구니·주문·Customer | 1~2일 |
| 3. PG 결제 연동 (개발) | 1~2일 |
| 4. 관리자 주문→캠페인 전환 화면 (수동 방식으로 단순화됨) | 반나절 |
| 5. 고객 마이페이지 | 반나절~1일 |
| 6. 리뷰·평점 + 노출수 보정 | 1일 |
| 사이트 분리 인프라 (새 프론트엔드 앱, 배포, 도메인) | 반나절~1일 |

**순수 개발 작업량 합: 대략 5~9일 분량.**

다만 실제 캘린더 기준 오픈까지는 이보다 더 걸릴 가능성이 높은데, **PG사 가맹 심사**가 병목이기
때문 — 통상 영업일 기준 며칠~2주 정도 걸리고(서류 상태에 따라 변동), 이 대기 시간은 개발과
병행할 수 있어서 전체 일정을 늘리지는 않지만 "언제 실제로 결제를 받을 수 있는지"는 이 심사
완료 시점에 좌우됨.

**결론: 개발 자체는 1~2주, 실제 오픈(결제 가능 시점)까지는 PG 심사를 포함해 2~4주 정도로 보는
게 현실적.** 심사는 최대한 빨리 신청해서 개발과 병행하는 걸 권장.
